## 1. P1：iOS 弹窗冲突仍有多处，前两次修复只覆盖了局部

**平台：以 iOS 为主。状态：源码确认存在冲突调用，具体卡死需要真机复现。**

- 全局提示在点击按钮时直接隐藏，然后 `setTimeout(callback, 0)` 执行下一步，没有等待原生 `onDismiss`。
- 自助注销的验证码输入使用原生 Modal，验证错误时仍在它上面展示全局 Modal。
- 管理员报名详情切换编辑页，会同时关闭一个原生 Modal、打开另一个；编辑内的“保存并通知”以及手动推送二次确认又会打开全局 Modal。
- 词典导入完成/失败时，在进度 Modal 尚未关闭时先显示结果提示。

可能表现：提示不可见、关闭后页面点不动、二次确认无法完成。不能认为更新检查和修改密码修好后，所有类似问题都已消失。

证据：[全局提示](I:/PARTTIME/AG/student-app/components/CustomAlertModal.tsx:66)、[注销](I:/PARTTIME/AG/student-app/app/settings/profile.tsx:213)、[报名编辑](I:/PARTTIME/AG/student-app/app/admin/manage-events.tsx:836)、[发送确认](I:/PARTTIME/AG/student-app/app/admin/manage-events.tsx:1352)、[词典导入](I:/PARTTIME/AG/student-app/app/tools/dictionary/settings.tsx:184)。

建议：统一原生弹窗调度，或让表单及内部确认共享一个展示容器；不要只增加固定延迟。验收应覆盖成功、错误、连续确认、取消、系统返回和重复点击。

## 2. P1：退出/切换账户后，旧请求仍可回写资料和前端权限

**平台：两端。状态：已本地模拟复现。**

`fetchProfile` 没有校验响应对应的用户是否仍为当前用户。`cancelled` 是按值传入的布尔值，不能阻止已经开始的旧请求；认证事件还直接传入 `false`。

复现场景：管理员资料请求未完成 → 退出 → 旧请求返回。模拟结果：`user === null`，但 `profile.role === 'super_admin'`，`hasAdminPermission('events.manage') === true`。

影响：旧资料/菜单显示、错误的前端权限判断、快速切换账户时状态串号。**这不是已经证明普通用户能绕过数据库权限**；服务端鉴权仍是另一道边界。

证据：[认证事件及资料读取](I:/PARTTIME/AG/student-app/context/AuthContext.tsx:97)、[资料回写](I:/PARTTIME/AG/student-app/context/AuthContext.tsx:149)。

建议：账户变化立即清空旧资料和权限，用用户 ID + 请求序号拒绝过期响应；旧请求的错误与 loading 状态也应丢弃。

## 3. P1：退出登录没有解除实际推送表中的用户绑定

**平台：两端。状态：客户端和迁移调用链确认，线上表状态未核验。**

退出只清空 `profiles.push_token`，没有清除 `push_tokens.user_id`。随后游客注册同一个设备 token 时，RPC 使用 `COALESCE(auth.uid(), 原user_id)`，仍保留旧用户归属。活动定向推送、管理员专属活动推送实际使用的是 `push_tokens`。

影响：退出后的手机仍可能收到前一个账号的报名修改/取消提醒；退出管理员账号后，设备也可能继续收到内部活动标题。重新登录其他账号会改变归属，但游客状态不会自动解绑。

证据：[退出逻辑](I:/PARTTIME/AG/student-app/context/AuthContext.tsx:231)、[token 注册](I:/PARTTIME/AG/supabase/migrations/012_admin_permissions.sql:442)、[活动收件人](I:/PARTTIME/AG/supabase/migrations/043_event_audience.sql:108)。

建议：针对当前设备解除账户绑定，保留需要的游客公开推送能力；处理离线退出和再次联网同步。另需检查 `signOut()` 返回的 `error`，当前调用未检查返回错误。

## 4. P1：普通登录用户的资料读取策略包含敏感列

**平台：服务端，两端均受影响。状态：仓库迁移定义确认，需只读核验线上 RLS/列权限。**

初始迁移允许所有 authenticated 用户读取全部 `profiles` 行，该表包含 `push_token`、学号等资料；后续迁移没有找到针对这条 SELECT 策略或敏感列的收窄。App 仍把实际 token 写入这张表。单独保护 `push_tokens` 表，不能阻止从 `profiles` 读取同一数据。

影响：若线上沿用这些规则，普通登录账户可通过接口读取超出其需要的其他用户资料和推送标识。App 界面不展示这些列不等于接口拒绝访问。

证据：[字段定义](I:/PARTTIME/AG/supabase/migrations/001_initial_schema.sql:12)、[读取策略](I:/PARTTIME/AG/supabase/migrations/001_initial_schema.sql:174)、[token 写入](I:/PARTTIME/AG/student-app/app/_layout.tsx:157)。

建议：公开资料与私人资料分离，或提供受控的公开资料视图/接口；推送 token 不放在可被普通用户列举的表中。先核验线上有效权限，不在生产库做越权写入试验。

## 5. P1：注销验证码只由客户端流程要求，删除 RPC 没有复核

**平台：服务端，两端均受影响。状态：迁移定义确认。**

UI 确实有多次确认、发送验证码和验证步骤。但 `delete_user_account()` 只检查 `auth.uid()`，随即删除该账号；没有要求最近完成重新认证的服务端凭据。持有有效会话的调用者可绕过 UI 直接请求删除自己的账户。

影响：验证码目前不是删除操作的服务端安全门槛；被拿到未锁定的已登录设备/有效会话时，额外验证码保护不完整。不是能删除任意他人账号。

证据：[删除 RPC](I:/PARTTIME/AG/supabase/migrations/042_restore_self_account_deletion.sql:5)、[客户端验证](I:/PARTTIME/AG/student-app/app/settings/profile.tsx:221)。

建议：保留现有 UI，同时让服务端验证短时、单次、绑定当前用户的重新认证证明。不要接受客户端自行传入的“已验证=true”。

## 6. P2：通知设置的多个开关未完整作用于实际推送

**平台：两端。状态：源码确认。**

- 主开关、免打扰、声音和震动主要写入本地；实际群发和定时活动发送没有按这些值选择接收人/声音。
- 前台处理只读取分类值，未读取总开关与免打扰等；且默认前台统一不弹 banner、不响铃。
- 后台系统通知不经过这段前台过滤逻辑。
- 微信文章推送使用 `category: 'general'`，设置页的独立 `articles` 开关没有对应到这条推送路径。
- 设置同步尝试更新 `notification_preferences`，但仓库没有找到该列的迁移；即便线上有该列，调用也没检查 Supabase 返回的 `error`。

影响：用户可能关闭了某类通知、声音或总开关，后台仍收到带声音的通知；跨设备设置也不可靠。不能把这些开关描述为已经完整生效。

证据：[设置页](I:/PARTTIME/AG/student-app/app/settings/notifications.tsx:185)、[前台通知处理](I:/PARTTIME/AG/student-app/app/_layout.tsx:44)、[群发](I:/PARTTIME/AG/student-app/lib/notificationService.ts:31)、[微信通知](I:/PARTTIME/AG/supabase/functions/wechat-sync/index.ts:367)、[定时活动通知](I:/PARTTIME/AG/supabase/functions/_shared/event-push-delivery.ts:30)。

建议：统一分类及设备/账号设置模型，在服务器生成收件人和通知内容时落实后台可执行的设置，并明确哪些提醒受系统权限控制。

## 7. P1：自习室接口失败时，模拟余座被当作正常数据展示

**平台：两端。状态：已本地模拟复现。**

接口异常后按手机时间和 `Math.random()` 生成占用率、余座和营业状态；返回类型没有数据来源标识。页面正常显示这些数值，刷新流程还可以提示成功。即使接口成功但缺少占用字段，也可能默认 0% 占用。

本地模拟：网络失败、固定下午时间、容量 100 → 返回“开放、占用 91%、剩余 9 座”。这不是缓存或真实余座。

证据：[模拟回退](I:/PARTTIME/AG/student-app/lib/studyroom.ts:487)、[页面加载](I:/PARTTIME/AG/student-app/app/tools/studyroom/index.tsx:303)、[余座展示](I:/PARTTIME/AG/student-app/app/tools/studyroom/index.tsx:514)。

建议：生产环境移除虚构数据回退；改为未知/暂时无法获取，或带时间戳的真实缓存。静态营业时间也应与实时状态明确区分。

## 8. P2：空教室的“今天”和课程时段没有统一罗马时区

**平台：两端。状态：源码确认。**

查询日期用 `toISOString()` 取 UTC 日期，但界面“当前”及课程起止时间用手机本地 `getHours()`。罗马凌晨可能取到前一天；手机在中国等时区时，固定上午/下午时段与转换后的课程时间也不一致。

例如罗马夏令时 00:30 对应 UTC 前一天 22:30，当前代码会拿前一天组成整日查询参数。

证据：[查询日期](I:/PARTTIME/AG/student-app/app/tools/classroom/index.tsx:886)、[时间转换](I:/PARTTIME/AG/student-app/app/tools/classroom/index.tsx:1021)。

建议：以 Europe/Rome 生成当天边界和查询时段，明确上游日期参数语义，覆盖凌晨及夏冬令时切换测试。

## 9. P2：空教室“当前可用”时间不会随着刷新前进

**平台：两端。状态：源码确认。**

`queryTimeRange` 用 `useMemo` 缓存当前分钟，依赖只有选择模式和手填时间。等待后下拉刷新课表，不会更新这个“现在”。

影响：09:00 打开，10:00 刷新，仍可能按 09:00–09:10 判断空闲。切换时间模式才重新计算。

证据：[当前时段计算](I:/PARTTIME/AG/student-app/app/tools/classroom/index.tsx:996)。

建议：刷新、返回前台或按合理周期更新当前时间，并处理跨日重新加载。

## 10. P2：其他网络请求仍可能长时间停留在加载状态

**平台：两端。状态：缺少应用层超时/取消的路径已确认。**

公交到站、空教室、自习室、汇率请求没有统一的应用层时限。自习室使用 `Promise.all`，任一接口迟迟不结束会拖住整个列表。火车公共超时封装在收到响应头时就清除计时器，不覆盖之后响应体读取；另有 Italo 请求直接使用 fetch。

不能说一定永久卡死，系统网络层最终可能超时，但 App 没有保证可接受的等待上限。

证据：[公交](I:/PARTTIME/AG/student-app/lib/tperService.ts:46)、[空教室](I:/PARTTIME/AG/student-app/app/tools/classroom/index.tsx:862)、[汇率](I:/PARTTIME/AG/student-app/app/tools/rate.tsx:232)、[火车封装](I:/PARTTIME/AG/student-app/lib/viaggiaTrenoService.ts:8)。

建议：统一覆盖响应体的超时、取消和过期响应保护。对写入操作超时，应提示结果未知并查询确认，不能简单认定失败后重复提交。

## 11. P2：从完全关闭状态点击推送，缺少恢复跳转的兜底

**平台：两端，具体行为需真机验证。状态：潜在风险。**

目前仅在 React effect 中注册通知点击监听，没有读取 `getLastNotificationResponseAsync`/同类初始响应，也没有明确的路由就绪队列。

影响：若点击发生在监听建立之前，系统启动 App 后可能只到首页，丢失文章/活动目标；是否触发取决于 SDK 和启动时序，不能凭静态代码断言每次必现。

证据：[通知点击入口](I:/PARTTIME/AG/student-app/app/_layout.tsx:179)。

建议：同时处理初始响应和运行中响应，等待导航就绪并对同一通知去重。分开验证前台、后台、杀进程启动及游客登录后继续跳转。

## 12. P2：手册编辑的未保存提示只覆盖页面返回按钮

**平台：两端。状态：源码确认缺少导航拦截，需真机验证具体手势。**

脏数据检查只在 `cancelEditing` 中，由左上角按钮调用。没有 `beforeRemove`/`usePreventRemove` 等拦截；全局 Android 返回直接 `router.back()`，iOS 侧滑也不经过这个按钮。

影响：编辑较长手册后使用系统返回，可能无提示丢失未保存内容。

证据：[手册返回逻辑](I:/PARTTIME/AG/student-app/app/admin/handbook-editor.tsx:120)、[按钮绑定](I:/PARTTIME/AG/student-app/app/admin/handbook-editor.tsx:240)、[全局返回](I:/PARTTIME/AG/student-app/app/_layout.tsx:204)。

建议：在导航层统一拦截离开动作；保存成功后的离开应解除拦截。

## 13. P2：文章管理只能看到前 100 条，没有后续分页

**平台：两端。状态：源码确认。**

管理员文章列表固定 `.limit(100)`，没有后续分页请求。发布/已删除分类各自只能拿到查询排序的前 100 条。

影响：数据积累后，较早文章无法从该页面管理或恢复；不代表数据库删除了它们。

证据：[文章管理查询](I:/PARTTIME/AG/student-app/app/admin/manage-articles.tsx:38)。

建议：补充分页和服务端搜索，排序使用稳定的唯一键。用户管理/反馈管理的一次性全量读取也应在增长后核查服务端行数上限。

## 14. P2：管理员报名修改已保存，刷新失败仍显示“保存失败”

**平台：两端。状态：源码确认。**

报名修改 RPC 成功后，仍在同一个 try 中等待名单重新加载；名单读取失败会进入统一 catch，标题显示“保存失败”。取消、转正等操作也存在“写入成功后刷新异常进入操作失败”的模式。

已有网络错误文字会提醒“结果可能已保存”，但标题和实际状态仍矛盾；部分非网络错误更难判断。

证据：[修改后刷新](I:/PARTTIME/AG/student-app/app/admin/manage-events.tsx:882)、[失败提示](I:/PARTTIME/AG/student-app/app/admin/manage-events.tsx:890)、[转正后刷新](I:/PARTTIME/AG/student-app/app/admin/manage-events.tsx:773)。

建议：分别处理写入、推送、刷新三个阶段。写入成功后应明确显示“已保存，列表刷新失败”，避免重复处理；已发出的推送不可因刷新失败再发一遍。

## 本轮确认已有的保护

- 活动报名服务端仍包含活动行锁、人数/车位校验、本人重复报名限制、版本冲突校验、历史表单快照和独立导出快照。
- 管理员功能有服务端权限检查；资料特权字段有保护触发器，因此没有把普通用户直接改自己 role 当作已发现漏洞。
- 词典索引导入具有事务及失败回滚；不能因存在导入进度弹窗问题就认定索引一定损坏。
- 火车代理限制了可访问的上游端点；不是任意 URL 代理。
- 本轮未找到新的确定的活动超售证据，但没有以此次静态审查替代真实并发验证。

## 建议处理顺序及验收

1. 先修复 1–5：统一弹窗、账户请求隔离、设备解绑、资料最小权限、服务端注销复核；第 7 项的虚构余座也应优先停止展示。
2. 再处理 6、8–11、14：通知真实生效、时间一致性、超时和保存结果反馈。
3. 最后处理 12–13，并扩充针对平台行为的回归测试。

真机回归矩阵至少覆盖：iOS/安卓正式安装包；前台/后台/杀进程；游客/普通用户/管理员；强网/断网/超时/响应晚到；重复点击；侧滑/系统返回；手机时区罗马/北京；通知允许/拒绝；连续切换账号。涉及注销和并发报名应使用专用测试账号和测试活动，不动真实报名数据。

测试通过标准不仅是“没有报错”，还应核对：结果提示可见、页面仍可交互、数据库状态正确、用户身份没有串号、推送发给正确设备、失败时没有生成伪数据。
