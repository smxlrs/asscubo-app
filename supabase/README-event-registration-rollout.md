# 活动报名修复：上线与验收

适用于 2026-09-25 的活动报名审查修复。2026-09-26 已确认线上安装 040、041；随后已执行 042 恢复自助注销接口、部署新版自动通知 Edge Function 并补齐 Vault 配置。当前项目无需重复执行这些步骤。仅 push GitHub 不会执行数据库迁移，也不会自动部署 Edge Function。

最新线上回归 37 项通过，临时数据全部回滚；数据库经 pg_net 调用新版通知函数的无发送探测返回 HTTP 200。测试过程没有发送真实推送，手机收件及 App 邮箱验证码注销流程仍需真机验收。详见 [线上测试及修复报告](tests/event-registration-live-report-2026-09-26.md)。以下执行顺序保留用于其他环境或重新部署。

## 执行顺序

请选择没有活动集中报名、没有即将到点的自动通知的时间段操作，并准备好包含本次修改的 App。新报名接口要求提交表单版本，修改接口要求提交记录版本；旧版 App 的报名和修改请求会被拒绝，防止错误解释旧答案或覆盖新数据。

1. **先部署新的自动通知 Edge Function**。在仓库根目录运行：

   ```powershell
   npx supabase functions deploy event-registration-start-notifications --project-ref avxzgaozbfeqttmhmlld
   ```

   如 CLI 未登录，先运行 `npx supabase login`。仓库的 `supabase/config.toml` 已为该函数配置 `verify_jwt = false`；函数自身检查内部密钥。Vault 中的 `event_registration_start_secret_key` 必须保存函数 `SUPABASE_SECRET_KEYS` 接受的有效项目 secret key；不要仅凭旧部署成功就假定此项仍存在。本项目已于 2026-09-26 补齐，并验证数据库到函数的鉴权通信。不要把密钥放进 App 或 Git。

2. 打开 Supabase SQL Editor，完整执行 [040_event_registration_hardening.sql](migrations/040_event_registration_hardening.sql)。
3. 040 成功后，完整执行 [041_event_notification_delivery.sql](migrations/041_event_notification_delivery.sql)。两个文件都带事务和 schema cache 刷新，可重复执行。任一步失败请保留完整报错，先处理失败，不要跳过后继续。
4. 完整执行 [042_restore_self_account_deletion.sql](migrations/042_restore_self_account_deletion.sql)，恢复可能未安装的自助注销函数。函数只删除当前登录者自己，复用 040 的名额释放触发器；不接受目标用户 ID。迁移本身不删除账号。
5. 用包含本次修改的 App / Expo 开发版本验证报名与管理页面。正式用户使用活动前，需要获得新版 App。

必须先部署新函数：旧函数接受 `event_id`，新任务发送 `job_id`。若先执行 041 而函数仍旧，旧函数可能把新请求误当作扫描所有活动。先部署新函数时，短暂收到旧请求只会拒绝；041 会重新登记仍启用的活动任务。

041 回填会安排仍满足条件的活动，包括“开放时间已经到达、开关仍开启、活动和报名尚未结束”的活动。已开启但不希望补发的旧活动，应先关闭自动通知开关。

## 本次规则

| 原问题 | 修复后的行为 |
| --- | --- |
| 1 | 数据库固定每条报名 1 人，同账号每活动只有 1 条有效本人报名；修改更新原记录。额外报名者仅在开启多人报名后允许，各有答案与备注；管理员可查看和导出提交者。 |
| 2、8 | 管理端、学生端、首页活动时间统一 Europe/Rome；全天活动包括结束当天，单日具体结束时刻保留；春季不存在的时刻拒绝，秋季重复时刻固定采用第二次。 |
| 3 | 活动与报名都校验版本。旧页面保存冲突时保留当前填写并提示重新加载，不覆盖新修改。 |
| 4 | 账号删除前释放本人及其代报名的名额，按开放状态处理候补，然后级联删除报名数据。 |
| 5、17 | 自动通知有持久任务、分批结果、独占处理和最多 5 次尝试；手动通知核对 HTTP 与逐条 Expo ticket，不再把失败报告为成功。 |
| 6 | 扩容、重开、新报名、学生修改先处理合资格的原候补。自选车按可满足的车位递补；管理员分车模式保留管理员决策，不自动转正。 |
| 7 | 提交和修改由数据库重新核对发布、状态、开放、截止、结束与容量。关闭显示“报名表已关闭”；总额满且无候补显示“名额已满”。开启候补时仍可明确进入候补。 |
| 9 | 认证令牌续期不会重新加载并清空未提交报名表；切换账号会清理对应页面状态。 |
| 11 | 删除新附件字段与上传入口，数据库拒绝新增附件。历史附件元数据只读保留，Storage 历史对象不自动删除。 |
| 12、13 | 学生候补可查看原选车；停用车从可选项中移除，但历史记录仍可显示其名称。 |
| 15、16 | 隐藏/归档活动不显示在学生“我的报名”；取消在取得活动锁后读取车辆，避免历史车辆记错。 |
| 18、19 | 后台通过每批 100 条的游标读取完整名单，界面每页 100 条，带翻页；搜索排序覆盖全部记录，导出读取完整事务快照。重连、回到前台及页面活跃时补同步，失败显示过期提示。 |
| 20 | 每条新报名保存当时的表单快照，后续修改和详情使用该快照；导出保留历史题目。新报名在数据库锁内检查表单版本，填写期间被改版的表单不能悄悄按新题目保存旧答案。 |

按用户决定：不增加离线导出（10）；不增加学生详情的到点自动刷新（14）。活动删除仍为软删除并保留管理历史；已取消报名的彻底删除仍是独立操作。

迁移前已丢失的旧题目名称或被旧程序忽略的具体结束时刻无法凭空恢复。已有报名的快照只能从迁移时的现有表单回填。旧的“一条记录包含多人”保持只读，可取消，不会被自动拆分或少算。

040 会校正未删除、未归档、未标记结束且明确关闭具体结束时刻的旧活动，把结束边界设为罗马时间结束日的 23:59:59.999。单日活动采用开始日期，夏冬令时切换日按当地下一次零点计算。旧版内部数组只有一个人、且人员表也恰好一人的答案会转换为单人格式；不明确的数据不会被猜测拆分。

## 自动通知资源与结果

没有启用自动通知的活动时，不创建全局每分钟扫描任务。每个启用活动有独立定时任务；完成或取消后撤销。失败一般约 5 分钟后重试，最多 5 次。后台可查看等待、处理中、已提交、部分失败、失败或取消。

“已提交”表示 Expo 接受，不代表手机实际收到。已记录成功的设备不会自动重发；如果 Expo 已接受但网络响应丢失，受控重试仍可能重复，这是外部推送接口无法提供严格恰好一次的边界。手动补发是广播，会再次通知此前成功的设备。
